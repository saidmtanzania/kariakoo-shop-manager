## 1. Architecture style

**Modular monolith** [C, A-001]: one NestJS API process (plus an optional worker process from the same codebase), one PostgreSQL database, one Next.js PWA. Modules have explicit boundaries and public services; no microservices without an approved decision.

```
                 ┌───────────────────────────────┐
  Browser / PWA  │ Next.js (apps/web)            │
  (desktop,      │  - App Router, React, Tailwind│
  Android)       │  - TanStack Query, RHF + Zod  │
     │           │  - Service worker + IndexedDB │
     │ HTTPS     └──────────────┬────────────────┘
     ▼                          │ /api/v1 (same site, cookie session)
 ┌──────────────────────────────▼─────────────────────────────┐
 │ NestJS API (backend)                                        │
 │  Guards: Session → ShopContext → Permission → Entitlement   │
 │  Modules: auth, users, shops, memberships, authorization,   │
 │  invitations, subscriptions, payments, products, inventory, │
 │  suppliers, purchases, customers, sales, expenses,          │
 │  cash-sessions, reports, audit                              │
 │  Prisma (PostgreSQL)                                        │
 └───────┬───────────────────────────────┬────────────────────┘
         │                               │
 ┌───────▼────────┐             ┌────────▼─────────┐     ┌────────────────────┐
 │ PostgreSQL 16+ │◄────────────┤ Worker (Nest     │────►│ Email / SMS /      │
 │ (single DB,    │  outbox     │ standalone app)  │     │ mobile-money       │
 │  shop-scoped)  │  polling    │ schedules, outbox│     │ providers          │
 └────────────────┘             └──────────────────┘     └────────────────────┘
```

Redis is **not** included initially. Background work uses a PostgreSQL-backed outbox and `@nestjs/schedule` (or `pg-boss`) in the worker. Add Redis only if a documented requirement (e.g. high-volume queues, distributed rate limiting across many instances) justifies it. [C]

## 2. Repository layout

As specified by the owner (see `AGENTS.md` and plan §6): `apps/web`, `backend`, `packages/shared`, `tests/{integration,e2e,architecture}`, `deploy/docker`, `docs/*`, `scripts`. Workspace tooling: **pnpm workspaces** [A-005, proposed].

Note: the owner's layout places the backend at `backend/` rather than `apps/api/`. This is kept as specified.

## 3. Frontend (Next.js)

- App Router, TypeScript strict mode, Tailwind CSS + shadcn/ui.
- Data fetching via TanStack Query against the REST API; forms via React Hook Form + Zod.
- All business rules are enforced on the server. Zod schemas in `packages/shared` are for UX validation only. [C]
- Rendering: primarily client-rendered authenticated app (works offline); public pages (landing, login) may be server-rendered.
- i18n: string catalogs from day one (`en`, `sw`), e.g. `next-intl`. [C]
- PWA: manifest, service worker (e.g. Serwist / Workbox), IndexedDB via Dexie for the offline sale queue and catalogue cache (Phase 10).
- Money formatting: TZS without decimals; amounts travel as **decimal strings** in JSON, never JS floats.

## 4. Backend (NestJS)

### 4.1 Module structure

Each module under `backend/src/modules/<name>/`:

```
controllers/   thin HTTP layer, DTO validation, permission decorators
services/      application services (use cases), transaction boundaries
domain/        pure business rules (unit conversion, costing, cash math)
repositories/  Prisma access; every query takes a ShopContext
dto/           request/response contracts
<name>.module.ts
```

Cross-module calls go through exported services, never another module's repositories. An architecture test (e.g. dependency-cruiser) enforces this. [A]

### 4.2 Request pipeline

1. **SessionGuard** — resolves the user from the session cookie (server-side session table) [A-003].
2. **ShopContextGuard** — reads the active shop from the session (not from client input), verifies an `ACTIVE` membership in an `ACTIVE`/restricted shop, loads the membership's effective permissions (cached per request).
3. **PermissionGuard** — `@RequirePermission('sales.create')` metadata; deny by default.
4. **EntitlementGuard** — `@RequireFeature('offline_sales')` checks the shop's subscription entitlements.
5. **ValidationPipe** — class-validator DTOs (or Zod via `nestjs-zod`) with whitelist + forbidNonWhitelisted.
6. Controller → service. Service receives `ShopContext { shopId, membershipId, userId, permissions }`.

### 4.3 API conventions [A-004]

- REST, versioned prefix `/api/v1`; OpenAPI generated by `@nestjs/swagger` and stored in `docs/api/`.
- Error format: RFC 9457 problem details `{ type, title, status, detail, code, errors[] , traceId }`.
- Pagination: cursor-based for lists (`?cursor=&limit=`), max 100.
- Idempotency: `Idempotency-Key` header required on sale creation, payments, purchase receipt, customer payments, refunds, subscription payments and offline sync.
- Money and quantities as strings (`"24000.00"`, `"12.000"`).
- Timestamps in UTC ISO 8601; business day boundaries computed in `Africa/Dar_es_Salaam` (UTC+3, no DST).
- IDs: UUID v7 (time-ordered) generated server-side; offline operation IDs are client UUIDs used only as idempotency keys.

### 4.4 Transactions and concurrency

- Financial and stock workflows run inside `prisma.$transaction` (interactive) at **READ COMMITTED** with explicit row locks or conditional updates [A-006]:
  - Stock decrement: `UPDATE stock_balances SET quantity = quantity - $q, version = version + 1 WHERE shop_id=$s AND product_id=$p AND location_id=$l AND quantity >= $q RETURNING ...` — zero rows ⇒ insufficient stock ⇒ rollback. When negative stock is allowed [D-007] the condition is removed.
  - Multi-line sales lock balances in a deterministic order (sorted product IDs) to avoid deadlocks.
  - Weighted-average cost update during receiving uses `SELECT ... FOR UPDATE` on the balance row.
- Idempotency records are inserted first in the same transaction (unique `(shop_id, scope, key)`); a conflict returns the stored response.
- External provider calls (mobile money, email, SMS) happen **outside** DB transactions, triggered via the outbox or after commit. [C]
- Database constraints back every invariant that can be expressed: unique SKUs per shop, `CHECK (quantity >= 0)` when negative stock disallowed, FK with `shop_id` composite keys where practical.

### 4.5 Outbox and background work [A-007]

- `outbox_messages` written in the same transaction as the business change (e.g. "send invitation email", "initiate STK push", "send receipt SMS").
- Worker polls with `FOR UPDATE SKIP LOCKED`, sends, marks done, retries with backoff, dead-letters after N attempts.
- Scheduled jobs: subscription expiry/reminders, pending-payment reconciliation, invitation expiry, idempotency-record cleanup, nightly ledger reconciliation checks. Every job iterates per shop with explicit tenant scope.

### 4.6 Payments architecture

- `PaymentProvider` adapter interface: `initiate()`, `verifyCallback()`, `queryStatus()`, `refund?()`. Implementations per provider/aggregator (selection [D-006]).
- Payment state machine: `INITIATED → PENDING → CONFIRMED | FAILED | EXPIRED`; `CONFIRMED → REVERSED`. Transitions are idempotent and recorded in `payment_events`.
- Callbacks: dedicated public endpoint per provider; verify signature/IP/secret; store raw event; dedupe on provider transaction ID; apply in a transaction.
- Reconciliation job queries pending payments older than N minutes.
- Used for both POS mobile-money sales and subscription payments, with separate ledgers.

## 5. Tenancy model [A-002]

- Shared database, shared schema, `shop_id` column on every shop-owned table.
- Primary enforcement: application layer — repositories require `ShopContext`; a Prisma client extension injects `shop_id` into `where`/`data` for tenant models and throws if missing.
- Defence in depth (recommended, decide in Phase 02): PostgreSQL Row-Level Security with `SET LOCAL app.shop_id` per transaction. Trade-off: extra complexity with Prisma connection pooling; mitigated by always running tenant queries inside a transaction that sets the variable.
- Platform-admin access uses a separate code path and is audited.

## 6. Offline architecture (Phase 10) [D-004]

- Designated device registered server-side (`pos_devices`); device receives a scoped, revocable device credential bound to shop + device, usable only for the sync endpoint.
- Catalogue snapshot with `catalog_version`; stock snapshot is advisory only.
- Queue in IndexedDB: `{ operationId, type: 'SALE', payload, createdAt, state, attempts, lastError, serverResult }`.
- Sync endpoint `POST /api/v1/sync/sales` processes operations in order, each idempotent by `operationId`; returns per-operation results.
- Conflict policy: if stock insufficient at sync time → `NEEDS_REVIEW` (sale recorded with flagged status and negative-stock exception) or `REJECTED` [D-004/D-007].

## 7. Deployment (to be selected after cost review) [D-020]

- Local: Docker Compose (postgres, api, worker, web, mailpit).
- Production candidates: (a) single VPS with Docker Compose + managed backups to object storage (lowest cost); (b) managed platform (e.g. Render/Fly/Railway) + managed PostgreSQL; (c) cloud provider with African region (AWS af-south-1 Cape Town) for latency.
- Requirements regardless of choice: TLS, automated backups with PITR, restore test, secrets in environment/secret store, log aggregation, uptime monitoring.
- Latency consideration: Dar es Salaam users; prefer hosting in Africa or Europe; validate with measurements.

## 8. Observability

Structured JSON logs (pino via `nestjs-pino`) with `traceId`, `shopId`, `userId` (no secrets, no tokens); health endpoints; error tracking (e.g. Sentry, optional); metrics on sale latency, sync failures, payment pending age.
